# OOC Development Procedure

Use this reference for every `OOC DEV:` implementation, maintenance, release, migration, deployment, repository, or Skill-change request.

## Boundary and authority

Development is not gameplay. Do not advance world time because source changed, turn a design discussion into campaign truth, or hide campaign repair inside a refactor.

Repository authorities:

- `runtime/`: deterministic engine, semantic commands, reducers, scheduling, persistence, APIs;
- `game/`: static mechanics, schemas, content, world/reference data;
- `state/`: mutable committed campaign truth;
- `plugins/shinobi-rpg/skills/shinobi-game-master/`: canonical ChatGPT GM procedure/presentation;
- `docs/`: current deployment/operations material only.

For broad architecture read `references/runtime-architecture.md` and `references/repository-map.md`.

## Development surface

Prefer an uploaded/local worktree for multi-file changes, migrations, cleanup, release work, or any task that benefits from execution and repository-wide tests. Use the GitHub connector as a bounded remote repository surface, not as a development workstation. When GitHub is the active surface, read `references/github-development.md`.

A user-provided repository ZIP is an editable source snapshot. Work inside a fresh extraction, run local verification, and return a complete package when requested. Do not write GitHub merely because a connector is available when the user asked for ZIP-only work.

## Implement one authority

For a requested change:

1. inspect current authoritative source/contracts;
2. identify the single writable owner of the behavior;
3. make the smallest coherent implementation;
4. update schema/template/contract/data/test files that define the same invariant;
5. run fast structural checks plus focused tests;
6. run deeper replay/soak diagnostics only when the changed subsystem warrants them;
7. package/commit/deploy/install only to the tier the user requested and the tools actually verify.

Do not introduce compatibility layers that become second writable authorities. Do not solve scale with silent first/last-N lifetime limits; use deterministic routing, paging/sharding, exact rehydration, or resumable causal work.

## Campaign repair and migrations

A confirmed bad saved fact is separate work:

1. diagnose/fix the source mechanic;
2. identify exact affected owners and provenance;
3. migrate/repair deterministically on a disposable copy first;
4. validate schemas, chronology, ownership, conservation, identities, and semantic before/after differences;
5. apply only the justified repair.

Never manually reconstruct large state JSON through a remote text connector. Never reroll an established person during representation migration.

## Release cleanup

For a release consolidation, make the current checkout describe only the current game.

- Keep current runtime/game/state authorities, deployment files, focused tests, and maintenance tools required to operate safely.
- Remove obsolete audits, migration instructions, probe workflows, duplicate manuals, revision-history prose, caches, generated bytecode, retired compatibility code, and legacy aliases only after proving active code no longer references them.
- Git history is the archive when Git history is being preserved; a clean release checkout does not need archaeological documentation.
- Current semantic campaign history under `state/` is game truth and is not "revision history" clutter.
- After deletion, search for stale references/imports and run the release gate again.

## Verification

Normal local loop:

```text
python tools/quick_check.py
python tools/test_changed.py <changed paths>
```

`quick_check.py` should remain a fast current-architecture gate, not a museum of historical phrase assertions. `test_changed.py` should route changed paths to maintained focused tests. A test not run is neither passing nor failing.

For a release candidate, also run the maintained runtime suite and any changed-domain replay/schema checks that materially increase confidence.

## Delivery truth

Track only verified tiers:

- `inspected`
- `edited`
- `locally verified`
- `packaged`
- `committed`
- `merged`
- `deployed`
- `MCP/app schema refreshed`
- `Skill installed`

Do not claim a higher tier because a lower one succeeded. A returned ZIP is not a GitHub update, deployment, or Skill installation.

## Git/Railway/runtime deployment

Live gameplay reads current truth through MCP, not GitHub. In the current shared source/campaign branch topology, **every non-state commit** advances the production branch and therefore triggers Railway so its persistent checkout can fast-forward to the same HEAD. Only runtime-generated state-only gameplay commits are excluded from deployment to prevent loops. A commit containing both state and any non-state path still deploys.

When MCP tool names or schemas change, verify the deployed server and the connected ChatGPT app/action snapshot separately. Deployment alone does not prove ChatGPT sees a new contract.

## Skill maintenance

Keep `SKILL.md` compact and always-relevant. Put specialized guidance in one-level references. Avoid duplicate root manuals.

For a Skill change:

1. edit the canonical Skill directory;
2. verify every referenced file exists;
3. run the Skill validator/package workflow when available;
4. package the complete Skill, not only changed files;
5. distinguish repository source, packaged Skill, and installed ChatGPT Skill.

A source/package update never implies the current installed Skill changed until installation is independently verified.

## Live-play feedback

Treat real play as integration testing. Classify a finding before changing code: Skill/presentation, runtime interface, runtime mechanics, static game data, projection/read model, campaign repair, performance/context efficiency, or feature/design. A technically correct system can still deserve improvement when real play exposes shallow choice, repetitive behavior, missing counterplay, weak autonomy, causal deadlock, poor discoverability, unnecessary context cost, or structurally story-starved flow.

Urgent false-truth, agency, knowledge, exploit, persistence, or blocked-intent issues should be surfaced immediately. Lower-severity craft findings should wait for a natural stopping point.

## Secrets

Never request, print, commit, or package PATs, passwords, OAuth tokens, Railway secrets, MCP preview secrets, or other credentials. Use configured secret stores/environment variables.
